# P0 第二轮：帧率瓶颈定位战役（2026-09-16，M4 实测）

方法：`[PERF] fps=… render_avg=…us render_max=…us loops=…` 每秒一行（`PW_PERF_PROBE=1`），
`fps` = 1 s 窗口内 `LV_EVENT_RENDER_READY` 次数，`render_avg` = `RENDER_START→RENDER_READY` 的
平均窗口（**含 flush 等待**，即"每帧占用时间"）。同页面、同注入状态、单 GUI/boot。

## 1. 关键发现：单帧成本与"画了什么"几乎无关

| 页面（数据在变） | fps | render_avg | 面板一帧（60 Hz） |
|---|---|---|---|
| 水平仪实时页（imubench，连续变化） | **48 / 49 / 48** | **17.1 ms** | 16.7 ms |
| 三轴图线页 | 13 | 19.2 ms | 16.7 ms |
| 轨迹页（bench 推-停） | 10~11 | 21.4 ms | 16.7 ms |
| 单摆页（bench 连续摆动） | 22 | 26.7 ms | 16.7 ms |

⇒ **每帧 ≈17~27 ms，与脏区内容无关**；`17.1 ms ≈ 一帧面板扫描周期`。
结论：`RENDER_START→READY` 里绝大部分是**等面板流水线**（拷贝 + 面板传输 + LCDC 握手），
CPU 光栅不是主导。**60 FPS 就是面板刷新率的硬上限**（用户在实时页看到的 60 FPS 属于该类状态）。
数据连续变化时本机稳定在 **48~49 FPS = 面板速率的 82%**。

## 2. 四个假设，逐个实测否决（都是负面结果，全部如实留档）

| # | 假设 | 做法 | 结果 | 判定 |
|---|---|---|---|---|
| 1 | "每帧全屏推屏 351 KB ≈ 14 ms" | 读 `fb_flush_start()` | 送面板的是 `p_fb->fb_clip`（**脏区**），全屏 `fb.area` 仅用于行偏移 | ❌ 假设错，脏区推屏 vendor 已实现 |
| 2 | 防撕 tear 行等待是主因 | `PW_LCD_SKIP_TEAR_WAIT=1` | fps **45**、render 16.4 ms（比 48/17.1 **更差**） | ❌ 否决，开关回 0 |
| 3 | 每帧 flush 次数多 | `PW_LIVE_STAGGER=1`（每拍只更新一处） | fps **47~49**、render 17.1 ms（**无差异**） | ❌ 否决，开关回 0 |
| 4 | 刷新周期 15 ms 与面板 16.7 ms 拍频 | `CONFIG_LV_DEF_REFR_PERIOD=16` | fps **47~49**、render 17.1 ms（**无差异**） | ❌ 否决，配置回 15 |

> 过程中还踩到一个**配置坑**：板级 defconfig 里 `CONFIG_LV_DEF_REFR_PERIOD` 出现了**两次**
> （我追加在前的被后面那条覆盖），kconfig 取最后一条 ⇒ 必须改规范位置那一条才生效。

## 3. 真正有效的改动（本轮唯一保留项）

`phywear.c` 主循环：固定 `usleep(10 ms)` → 自适应休眠（`PW_LOOP_SLEEP_MAX_MS=2`）。

| 页面（静置、数据不变） | 基线 | 改后 |
|---|---|---|
| 实时数值页 | fps 26 / 28，loops 26 / 28 | fps **33~36**，loops 33~36（**+30.8%**） |
| 轨迹页 | fps 8 / 9，loops 57~59 | fps 10 / 11，loops 203 / 211 |
| 主页 root | fps 3，loops 75~80 | —（近乎静态，不适用） |

机制：静置页面本就没内容可画，LVGL 的发帧节奏由"主循环多久回来一次"决定；固定 10 ms 把每帧
硬生生推迟最多 10 ms。改自适应后静置页也接近面板节奏。

## 4. 距 60 FPS 还差多少（可执行结论）

连续变化态：**17.1 ms/帧 vs 16.7 ms 预算 —— 只超 0.4 ms**。也就是说
**只要把每帧的流水线占用再压掉 ~0.5~2 ms，就能在"数据连续变化"的页面上稳定到 60 FPS**。
可动的点（按性价比）：

1. **缩小每帧的脏区并集**（脏区越小 → 拷贝 + 面板传输越短）：实时页三个角度标签与水平仪小卡
   分散在页面左右两侧，并集几乎覆盖整屏宽 × 200+ 行。把读数聚拢成一列/一块，可显著减小并集。
2. **提高面板扫描率**（CO5300 帧率寄存器 / LCDC 时序）——这是唯一能突破 60 上限的路，
   属面板级改动，需数据手册与人眼验收，**未做**。
3. 降低单帧光栅量（画布类页面）：影响的是 19~27 ms 那几页，对已达 48 的实时页无益。

## 5. 回退面

- 主循环休眠：`PW_LOOP_SLEEP_MAX_MS` 改回 10（一行）＝ 完全恢复基线行为。
- 三个实验开关默认值均为"原行为"：`PW_LCD_SKIP_TEAR_WAIT=0`、`PW_LIVE_STAGGER=0`、`PW_PERF_PROBE=0`。
- 圆角 `PW_CARD_RADIUS=14`（A/B 证明 0 无收益，保留观感）。
- 仓库锚点：tag `pre-p0-20260916`（本轮之前）、`pre-motion-skill-20260916`（未动）。

## 6. 收尾审查（P0-6/P0-7）：主机侧那 ~4 ms 的定性 —— **无可挖项，结案**

**只读审查对象**：`drv_lcd_fb.c` / `lv_lcd.c` 的每帧等待链。

| 审查点 | 实测/代码事实 | 判定 |
|---|---|---|
| 每帧等待方式 | 全部是**事件驱动**：`nxevent_tickwait` / `nxsem_tickwait_uninterruptible`；`FB_COPY_EXP_MS=1000`、`FB_FLUSH_EXP_MS=5000`、`LCD_FLUSH_EXP_MS=5000` 只是**兜底超时**，命中即提前返回 | 无固定睡眠可挖 |
| 防撕裂行等待粒度 | 行中断设置为**每 10 行**一次（`interval_lines = 10`，源码注释说明调大反而"idle waiting"更多）⇒ 10 行 ≈ **0.37 ms** | 粒度已足够细 |
| 渲染与推屏是否串行 | **已重叠**：`write_fb_cb_done_send()` 先 `fb_flush_start()`（启动 LCDC）再 `write_fb_cb2() → lcd_flush_done() → lv_display_flush_ready()`；vendor 注释明确写了"必须由 LVGL 线程启动 LCDC，从中断里先 flush_ready 会让下一次 flush 与末次拷贝竞争" | 设计上已解耦 |
| 主循环休眠 | `PW_LOOP_SLEEP_MAX_MS` **0（纯忙等）vs 2 ms** 同口径 A/B：fps **48~49 / render 17.0 ms** 对 **48~49 / 17.1 ms** —— **完全相同** | 节拍不由主循环决定 |

**结论（P0 规划收尾）**：本队页面在"数据连续变化"态的 **48~49 FPS** 与 LVGL 官方跑分的轻负载上限
**56~63 FPS** 之间，差的不是某一处可修的软件开销，而是**每帧 17 ms ≈ 一帧面板扫描周期**这条固有节拍。
面板 CO5300AF-01 手册已确认 **VFR=60 Hz 且无帧率控制寄存器**，故：

- **60 FPS 是这块屏的物理上限**（"稳定 60 以上"不可达）；
- **48~49 FPS（上限的 82%）是当前硬件+配置的正常区间**，作为本项目的帧率结论；
- 软件侧已把可以拿的都拿了：**静置态页 +30.8%**（主循环自适应休眠），并**否决并留档 6 个假设**
  （全屏推屏 / 防撕等待 / flush 次数 / 刷新周期 / 脏区并集 / 主循环休眠）。

**未来若要再提速，只有两条非软件路径**：换更高帧率的面板，或确认 TE 走线后开 VSYNC（只治撕裂、不提上限）。
