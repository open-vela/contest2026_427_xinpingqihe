# P1-2 动效查表证据包 — 2026-09-16

## 1. 真机计时（`phywear motionbench 20000`，SF32LB52）

见 `motionbench-device.txt` 原文：

| 实现 | ns/次 | 说明 |
|---|---|---|
| 查表（PW_MOTION_USE_TABLE=1） | **151.25** | 整数索引 + 线性插值，表在 flash（516 B） |
| 解析式（expf+sinf+cosf） | **2088.40** | 同一份代码里的对照实现，始终编译 |
| 倍数 | **×13.8** | 每次调用省 **1937 ns** |

主机（x86-64 -O2）同代码对照：0.59 vs 6.40 ns/次（×10.8），见 `docs/10` §1.3。

## 2. 诚实结论：**查表不是帧率杠杆**

把上面的数字放回真实调用量级：

- LVGL 的动画 path **每帧每对象调用一次**。一次 320 ms 的动效 ≈ 19 帧 ≈ **19 次调用**，
  省下 19 × 1937 ns ≈ **37 µs**（一帧预算是 16.7 ms，占比 0.2%）。
- 即便同屏 3 个对象同时动、每秒重起动一次，合计也只有 **~0.1 ms/s** 量级。
- 因此：查表法的价值是**成本确定性**（无 libm 抖动、代码可控、表仅 516 B），
  **不是**提升 fps 的手段。把它当帧率优化去宣传是错的 —— 真正压帧率的是
  `update_fb()` 每帧全屏推屏（351 KB @25 MB/s ≈ 14 ms）与圆角回退 SW，
  见上一轮《实验性审查报告》P0-1/P0-2。

`imutraj-anim.png`：切到「轨迹」页时图形卡做查表弹簧滑入（320 ms），
截图取在动画结束之后 —— 图形卡停在最终位置（y=46），无偏移、无残影、无卡死，

即单次单对象动效**测不到帧率退化**。
