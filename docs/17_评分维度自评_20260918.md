### 2.1 技术难度 26.5 / 30

**得分依据（逐条，均有证据目录）**

1. **驱动 / BSP 级修复四件**（`docs/09` §3.4「硬件适配」，2026-09-19 复核）：EPIC 栈上触控失效（官方栈缺陷，本队修复）；启动偶发卡死的时钟 / 晶振建立时序竞争（补一段等待，具体时长（缺数据，需补））；麦克风增益过低（量化值（缺数据，需补））；喇叭换频爆音（音量爬坡淡入淡出）。这些不是改配置，是在 BSP 和驱动里找竞争条件。
2. **蓝牙从"no-go"翻案到 B1/B2/B3 全部真机实测通过（2026-09-18）**（`docs/16` §13.6e，无日期，需补；`docs/evidence/bt-b3-20260918/`）。两个根因都**不在配置层**：
   - 根因一：NuttX 的 fd 表按 `task_group` 存放，而 zblue port 把 HCI 命令的 `write()` 放在 Zephyr 系统工作队列线程里，与 `h4_open()` 不同组，导致跨组写恒 `EBADF`，控制器一个字节都没收到；表象却是"控制器不回包"，`-EIO` 是 `hci_cmd_done(..UNSPECIFIED)` 伪造 status 造出来的假象，极易误判成硬件坏。修法：`h4_send()` 只入队，`write()` 交给同组的 `h4_rx_thread`。
   - 根因二：`gatt_notify_mc()` 漏赋 `data.handle`，通知帧 value handle 恒为全零，被宿主 BlueZ 静默丢弃——设备侧 `notify rc=0` 全绿、宿主 0 包，"发出去了"不等于"对端收到了"。修法：补该赋值，通知帧句柄恢复正常，宿主正常收包。
3. **面板 60 Hz 物理上限定案**（`docs/evidence/p0-20260916/`，2026-09-16；`docs/11_面板时序与VSYNC方案_待批.md`，无日期，需补）：CO5300AF-01 的 VFR=60 Hz（Typ.）就是物理上限，无帧率控制寄存器、TE 未走线，"60 以上"物理不可达；主机侧多轮优化假设逐条实测否决（原始输出 `ab-*.txt`），含"每帧全屏推屏"这类一开始被误判的假设。结论是**主机侧已无可挖项**，而不是"没调好"。
4. **自研算法库**（`docs/09` §3.3）：Mahony 显式互补滤波（MARG 9 轴，自写实现，陀螺零偏显式积分状态、磁力计只修偏航）；六面法加速度标定 + 磁椭球拟合（硬铁软铁、代数拟合 + 特征分解），全程流式充分统计、不存原始样本；FFT（radix-2 迭代 Cooley-Tukey，复用于三类频谱）；自相关测周期、向心加速度过原点最小二乘、阈值滞回事件对。
5. **多传感器与音频适配**（`docs/09` §3.4）：CO5300 AMOLED + EPIC、FT6146 触控、LSM6DSL、MMC5603、LTR303、AUDCODEC DAC/ADC、扬声器、麦克风，全部走 NuttX 字符设备接入 LVGL 应用。
6. **PPP over BLE 端到端打通到 IP 层（2026-09-18 深夜，N1/N2 达成）**（`docs/16` §13.6e、`docs/evidence/bt-ppp-e2e-20260918/`）：设备侧 `ppp0` 起来并 RUNNING，设备上 `ping` **3 sent / 3 received，0% 丢包**，一键判定 `pw_bt_ppp_e2e.py` **6/6**；宿主侧是**自实现的用户态 PPP 对端**（LCP + IPCP + ICMP + HDLC/FCS 成帧，不需要 root）。
7. **资源墙的解法是结构性的**（`docs/09` §3.5，2026-09-18 23:20 构建）：本板一度卡在 SRAM 悬崖（历史值不外引），真因不是调参，而是两处没有显式配置的栈继承了板级默认栈尺寸（NuttX 默认值（缺数据，需补）），改成显式配置后一次省下大头（具体字节（缺数据，需补）），PPP 两个任务栈再改从堆 / PSRAM 上要；最终出货构建 SRAM **483,356 B / 512 KB（92.19%）**（data 18,836 + ramfunc 10,376 + bss 454,144），反而低于加蓝牙之前的基线。

**扣 3.5 分在哪**：EPIC 硬件加速本身来自官方 PR（官方 PR #31/#41/#121，非本队原创，`docs/09` §3.3 已标注），这部分不计原创；姿态与轨迹的精度只有"与加速度计独立解算一致"这类内部一致性证据，**没有转台真值、没有手推真值**（转台/直尺实测：（缺数据，需补）），所以精度指标不敢往上报；端侧无自研推理模型，AI 能力在端侧是规则与算法，不做假 AI。

**30 分钟内能补**：把两个蓝牙根因各写一段"现象—误判路径—根因—修法—复测计数"的固定格式摘要，塞进 `docs/03` §3.3。评委看技术难度最先看的就是"你到底踩过什么坑"，这两段是最硬的料，现在埋在 `docs/16` 长文里。

## §三 三条提分性价比排序（改动量 ÷ 得分）

排序原则：**单位耗时换到的分数（或避免的扣分）从高到低**。括号里是"改哪份文件 + 预计耗时"。

**第 1 条：把 README 与 `docs/09` 残留的旧数字统一到定稿口径（防"整表扣分"）**
改 `README.md`、`docs/09` §2 摘要与 §3.5 测试表里的历史帧率、历史资源占用、历史证据组数、旧页面计数（凡与定稿表不一致的一律替换或标注"历史值不外引"）；预计耗时 **30 分钟**。
为什么排第一：这一条不直接加分，但它防的是**最贵的扣分**——评委一旦发现 README、报告、自评三处数字打架，会把"数据可信度"整体降级，六个维度一起遭殃。改动量最小、风险对冲最大。收益记为"全维度防扣"。

**第 2 条：报告导出 PDF + 补作品展示照片（清单在 `docs/07`）**
改 `docs/PhyWear_技术报告_官方模板.docx` 的导出产物 + 新增 `docs/evidence/showcase-*/` 一组照片；预计耗时 **1 小时**（导出半小时、拍照半小时；若本机无 libreoffice 则换机导出）。
预计收益：展示效果 +1~2，项目完整度 +1。这是纯执行活，不需要新实验、不需要新代码。

**第 3 条：真手机（Android / iOS）上点一次 BLE，留证据目录**
改 `docs/16` §13.6e 的"待办"为"已验" + 新增 `docs/evidence/bt-phone-*/`（截图 + 串口原文 + `SHA256SUMS.txt`）；预计耗时 **半天**（需人工 + 一部手机 + nRF Connect 类工具）。
预计收益：项目完整度 +1，技术难度 +0.5，商业潜力的"推广可信度"顺带受益（"手机能连"是向学校 / 科技馆演示的第一句话）。宿主 BlueZ 已验证同一套 ATT 动作，风险低，只差真机实测。
