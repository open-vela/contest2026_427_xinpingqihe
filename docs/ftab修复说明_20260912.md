# XIUFUBANFA —— 「只打印 SFBL 不启动」的修复存档（2026-09-12）

> **这是一次史诗级修复。** 它推翻了我们 9/11 得出的"硬件/供电问题"结论。

## 一、结论（一句话）

**真因：板子 flash 起始 `0x12000000` 没有 ftab（FlashTable），出厂就是空的。**
SiFli ROM 必须先读到 ftab，才知道二级 bootloader 的 base / size / **xip_base**，
以及该「拷到 RAM 执行」还是「原地 XIP」。拿不到有效 ftab → ROM **只打印 `SFBL`**，
然后停在串口下载模式等待 `ATSF32`。

**误判信号**：此时 `sftool` **仍然能秒连**（`Connected success!`）——
芯片、UART、ROM 全都正常，只是没东西可跳。我们当时把"擦空应用区也一样"
误读成了"与固件无关 ⇒ 硬件问题"，**漏掉了"板级 / flash 布局"这第三种可能**。

## 二、修复（两步，顺序不能反）

```bash
# ① 先写改好的 ftab
sftool -c SF32LB52 -p /dev/ttyUSB0 -b 1000000 \
  --before default_reset --after no_reset \
  write_flash ftab_openvela.bin@0x12000000

# ② 再写固件
sftool -c SF32LB52 -p /dev/ttyUSB0 -b 1000000 \
  --before default_reset --after soft_reset \
  write_flash cmake_out/<配置>/nuttx.bin@0x12010000
```

**ftab 改了什么**：16 字节条目 `[flag, base, size, xip_base]`，把 bootloader 那条的
`xip_base` 从 `0x20020000`（拷到 RAM）改为 **`0x12010000`**（原地 XIP），
以匹配 openvela 链接脚本 `flash ORIGIN = 0x12010000`。

- `ftab_official_v1.2.2.bin` → `ftab_openvela.bin` 只差 **2 处、各 2 字节**（偏移 `0x3E/0x3F` 与 `0x7E/0x7F`）
- 可用 `cmp -l ftab_official_v1.2.2.bin ftab_openvela.bin` 复核

**修复后启动序列**：
```
SFBL
ABCD                        ← 我们固件自己的启动进度标记（sifli_start.c 逐字符打）
ADC calibration data missing, use defaults
INFO: NOR MTD registered at /dev/config0 (offset=2464 blocks=1024)
NuttShell (NSH)
nsh>
```

> `ABCD` 不是 ROM 打的，是 `vendor/sifli/chips/sf32lb52/sifli_start.c` 里
> **逐字符输出**的进度标记，所以全源码 grep `"ABCD"` 找不到 —— 这也是当时误判的原因之一。
> A=data 段就绪，B=cache 使能，C=HAL_Init 完成，D=即将 nx_start()。

## 五、Skill 里的重要事实（与我们现有认知的差异）

1. **官方黄山派板目录是 `lckfb_huangshan_pi`**，我们一直用的 `sf32lb52_lchspi_ulp` 是另一套。
2. **官方 README 说"没有独立 bootloader 或分区表"是不准确的** —— 必须自己补 ftab。
3. **不要用 `erase_flash`（整片擦除）**；需要清理只擦应用区：`erase_region 0x12010000:0x700000`
4. **30P 排针的 5-6、7-8、11-12 三组必须插跳线帽**（原厂为串电流表故意断开），否则供电通路是断的。
5. 该 Skill 对应的是**原版（stock，CPU 渲染）**，EPIC GPU 加速版本尚未合入 ——
   **我们的 PhyWear 走的是 EPIC 路线，属于"加速版"**，两者能力不对等，不要直接对标帧率。
