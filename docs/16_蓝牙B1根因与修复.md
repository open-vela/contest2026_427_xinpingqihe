## 1. 一句话根因

**zblue 的 NuttX port 把 HCI 命令的 `write()` 放在 Zephyr 系统工作队列线程里执行，
而 NuttX 的文件描述符表挂在 `task_group` 上 —— 该线程与调用 `bt_enable()`
（进而在 `h4_open()` 里 `open("/dev/ttyHCI0")`）的任务**不是同一个组**，
于是每一次 `write()` 都返回 `EBADF(errno=9)`。控制器从头到尾**一个字节都没收到**。**

`bt_enable()` 返回的 `-EIO(-5)` 是**假象**：它是
`hci_core.c` 在 `bt_send()` 失败后调用
`hci_cmd_done(hdev, opcode, BT_HCI_ERR_UNSPECIFIED /*0x1F*/, buf)`
**伪造**出来的一个 status，再被 `bt_hci_cmd_send_sync()` 翻译成 `-EIO`。

## 3. 代码级定位（可独立复核）

| # | 事实 | 文件:行 |
|---|---|---|
| 1 | fd 表按 **task_group** 存放 | `nuttx/fs/inode/fs_files.c:826` `file_get2()` → `fdlist_get2(nxsched_get_fdlist(), fd, …)` |
| 2 | `nxsched_get_fdlist()` 取的是 `tcb->group->tg_fdlist` | `nuttx/sched/sched/sched_getfiles.c:88` → `:51` `nxsched_get_fdlist_from_tcb()` `ret = &group->tg_fdlist;` |
| 3 | Zephyr 线程 = NuttX **pthread**，与**创建它的任务**同组 | `external/zblue/zblue/port/kernel/thread.c` `k_thread_create()` → `pthread_create()` |
| 4 | 系统工作队列线程由 `SYS_INIT` 在**板级启动阶段**创建 | `external/zblue/zblue/kernel/system_work_q.c` `SYS_INIT(k_sys_work_q_init, POST_KERNEL, …)`；由 `z_sys_init()` 调用，而 `z_sys_init()` 来自 `vendor/sifli/chips/sf32lb52/sf32lb52_bth4.c` `sf32lb52_bt_zblue_init_once()` |
| 5 | HCI 命令 TX 走系统工作队列 | `hci_core.c` `bt_tx_irq_raise()` → `k_work_submit(&hdev->tx_work)`；`tx_work_handler` → `process_pending_cmd` → `hci_core_send_cmd` → `bt_send` |
| 6 | port 的 `h4_send()` 直接在该线程里 `write(h4->fd,…)` | `external/zblue/zblue/port/drivers/bluetooth/hci/h4.c` `h4_send()`（修复前） |
| 7 | 失败被压成 `-EINVAL`，再被伪造 status 掩盖 | `h4.c` `h4_send()`：`ret != len ⇒ ret = -EINVAL`；`hci_core.c:3177-3184` `hci_cmd_done(… BT_HCI_ERR_UNSPECIFIED …)`；`hci_core.c:509-525` `status → -EIO` |

**三个可疑点的判定（任务 1 要求的按序证伪）**

| 可疑点 | 判定 | 依据 |
|---|---|---|
| ① UART 流控 RTS / 波特率 | **已证伪（不适用）** | `/dev/ttyHCI0` 根本不是物理 UART：`nuttx/drivers/serial/uart_bth4.c` 是**伪串口**，后端是 `vendor/sifli/chips/sf32lb52/sf32lb52_bt_adapter.c` 的 **L2H/H2L 硬件邮箱 + 共享内存环**。无波特率、无 RTS/CTS、无 DMA。`CONFIG_UART_BTH4` 下没有任何流控符号。 |
| ② H4 初始化时序 / LCPU 上电 | **已证伪** | `[BTA] controller_enable enter status=1 queue_open=0` → `lcpu_power_on -> 0`（500 ms 懒上电）→ `host_send_packet -> ret=0`，全程正常。修复前后都走到这里；修复前是**写 fd 就失败**，压根没进厂商驱动（`[BTD]` 一行都没有）。 |
| ③ host 栈重配 UART | **已证伪** | port 的 `h4.c` 只 `open()` + `read()/write()`，不改任何 termios。真正的断点在**进程/任务上下文**，不在传输配置。 |
| **④（新增，真凶）跨 task_group 的 fd** | **已证** | 见 §2.3 与 §3。 |

## 4. 修复

**文件**：`external/zblue/zblue/port/drivers/bluetooth/hci/h4.c`

**思路**：让**打开 fd 的那个线程组**独占所有 fd I/O。`h4_open()` 创建 `h4_rx_thread`
（与该组同组），所以把 TX 也交给它：

1. `struct h4_data` 增加 `struct k_fifo tx_fifo;`
2. `h4_open()` → `k_fifo_init(&h4->tx_fifo);`（在创建线程前）
3. `h4_send()`：只 `net_buf_push_u8()` 补 H4 type 字节 + `k_fifo_put(&h4->tx_fifo, buf)`，**不再 write**，返回 0（缓冲所有权移交驱动，符合 Zephyr 驱动契约）
4. 新增 `h4_hw_tx()`：真正的 `btsnoop_log_capture()` + `h4_send_data()` + `net_buf_unref()`
5. `h4_rx_thread()` 每轮循环开头 `while ((buf = k_fifo_get(&h4->tx_fifo, K_NO_WAIT))) h4_hw_tx(h4, buf);`

**代价**：`h4_data` +24 B（k_fifo），TX 最坏 +1 ms 延迟（RX 线程本身 1 ms 轮询节拍）。

## 5. 顺带确证的两件事（避免以后重复踩）

1. **`CONFIG_BT_DEBUG_LOG` 本板原先没开** ⇒ `port/include/zephyr/logging/log.h`
   把整个 host 栈 + `h4.c` 的 `LOG_ERR/LOG_WRN/LOG_INFO/LOG_DBG` **全部展开成空语句**。
   这就是为什么 `bt_enable()` 失败时串口上一个字都没有，只剩
   `hci_core.c:3388` 那句裸 `syslog("dev:%d: Sending HCI_RESET")`。
   树里其它所有用 H4 的板（goldfish / r528 / bes）都开了 `BT_DEBUG_LOG`。
   → 诊断期设 `CONFIG_BT_DEBUG_LOG=y` + `CONFIG_BT_DEBUG_LOG_LEVEL=4`（只放 err/wrn）。
2. **控制台提示符是 `vela>`（ai_agent CLI），行结束符必须是 `\n` 不是 `\r`**。
   `\r` 会被当成普通字符，命令不执行（现象：只有回显、没有输出）。
   取证脚本 `tools/phywear/pw_serial.py` 已按此实现。

### 11.2c 采样策略 + B3 判定器的一处假 PASS（都已修）

1. **采样只在有人看的时候做**：`pw_sample_once()` 改成
   - `g_nfy_on`（有订阅者）时才由 500 ms 的 `k_work_delayable` 周期采样；
   - 没有任何人订阅时不采样 —— 别为了没人看的数据每 500 ms 去开一次 `/dev/lsm6dsl0`；
   - **GATT 读的时候现采一次**（`pw_read_sensor()` 里调），这样手机点"读"拿到的是
     当下这一秒的值，而不是上一轮 notify 的旧值。

2. **B3 判定器曾经假 PASS（已修，值得记）**：`cmd_in` 的模式是
   `[bt] cmd #n (x B): '...'`，而**服务端自检自己也会写一条命令**，
   于是"没有手机"也会判"手机写入命令 PASS"。
   两处一起改：自检改用专用命令名 `selftest`（并打印
   `[bt] cmd: selftest ok (设备侧自检，非手机写入)`），判定器把 `notify_on` /
   `cmd_in` 两项**限定在最后一次 `B3 connected` 之后**才算数。
   修后负对照正确变成 3 项 FAIL（`22_b3-verifier-negative-control-v2.log`）。
   ⇒ 教训：**"判定器报 PASS"本身也要有负对照**，否则它只是在骗自己。

### 11.2d 第三轮：限时采样 + 出货固件的 A/B 复证 + 逐页回归

1. **限时采样（避免堵住 BT 工作队列）** —— 这是个真问题：
   GATT 回调与周期通知都跑在 **Zephyr 系统工作队列线程**上
   （`bt_recv` → `k_work_submit(&hdev->rx_work)` → `rx_work_handler`，
   `CONFIG_SYSTEM_WORKQUEUE_STACK_SIZE=4096`），而
   `pw_sensors_read_imu_oneshot()` 内部最坏要走「3 次读 + START + 5 次读」≈160 ms。
   原来我再套 6 次重试 ⇒ 最坏能把工作队列堵 ~1 秒，连带推迟 HCI 命令 TX 与收包处理。
   改法：`pw_sample_once(int strict)`
   - `strict=1`（GATT 读 / 自检）：用户主动触发，最多 4 次重试；
   - `strict=0`（500 ms 周期通知）：**只读一次**，样本不合理就**不更新** `g_pkt`
     （保留上一个好值），绝不为了一条通知去堵队列。

2. **出货固件里复证 A/B 两半**（同一固件）

### 11.2f 第五轮：修掉 H4 RX 的一颗静默哑弹（`len == -EAGAIN` 永假）

**问题**（`port/drivers/bluetooth/hci/h4.c` 的 `h4_rx_thread`）：

```c
len = read(h4->fd, ...);
if (len < 0) {
    if (errno == EINTR) continue;
    if (len == -EAGAIN) { usleep(500); continue; }   /* ← 永远为假！ */
    LOG_ERR("Reading hci failed, errno %d", errno);
    close(h4->fd); h4->fd = -1; return;              /* ← 关 fd + 杀线程 */
}
```

`read()` 出错时返回 **-1**、EAGAIN 在 **errno** 里，所以 `len == -EAGAIN` 恒假 ⇒
**任何一次瞬时读错误**都会走到 `close(fd) + return`。
而 B1 的修复把 **TX 也交给了这个线程**（`h4_send` 只入 `tx_fifo`，由该线程写 fd），
所以一旦发生：**RX 线程没了 + fd 关了 + TX 也发不出去 = 整个蓝牙栈静默死亡**。
更要命的是出货配置**没开 `CONFIG_BT_DEBUG_LOG`**，上面那句 `LOG_ERR` 被编译成空语句，
连一行提示都没有 —— 在 B3 现场只会表现为"手机突然连不上/读不到"，几乎无法归因。

**修法**：
- 修正判据：`errno == EAGAIN || errno == EWOULDBLOCK` ⇒ `usleep(500); continue;`
- 其它错误不再当场放弃：累计 `h4->rx_errs`（新增字段，成功一次清零），
  连续 < `PW_H4_RX_ERR_MAX`(=50) 次就打印并重试；
- 真要放弃时用**无条件 `printf`**（不走 `LOG_*`、不走 `PW_H4_TRACE`）留下原文：
  `[H4] rx read 连续失败 %u 次 (errno=%d) —— 放弃并退出 RX 线程；此后 RX / TX 都会停`

**代价**：`h4_data` +4 B（实际被对齐吸收，SRAM 仍 **494,268 B 未变**）。
**验证**：出货固件复跑 —— `bt_enable rc=0` / B2 三行 rc=0 / `SELFTEST PASS`
（`|a|=1015 mg`）/ 全程 `rx read errno` 计数为 **0**（正常路径不受影响）；
fps 12 不变、root 截图与改动前逐字节相同。
（这条路径无法在实验室里"人为触发"，所以只能靠代码审读 + 正常路径无回归来兜；
证据是 `29_rx-err-handling-hardened.log`。）

> 这是本轮"专挑 B3 会走到的路径"审读时挖出的**第二颗**同型哑弹
> （第一颗是 R3 的工作队列阻塞预算）。共同点：**在出货配置下都是静默的**。

### 11.2g 第六轮：把"采样阻塞预算"从次数改成**时间**，并把它量出来

R3 已经把**周期**通知路径压成"只读一次"，但 **GATT 读路径**（手机点"读"触发）当时还是
"最多 4 次"——而 `pw_sensors_read_imu_oneshot()` **一次**最坏就 ~160 ms
（内部 3 次读 + `SNIOC_START` + 5 次读），4 次 ⇒ 最坏 ~640 ms 把 BT 工作队列按住，
手机连着时可能表现成卡顿甚至掉线。

改法：`strict` 路径改成**按时间**限
（`PW_SAMPLE_BUDGET_MS=200`、只有剩余预算 ≥ `PW_ACC_MIN_RETRY_MS=100` 才重试），
拿不到就保留上一个好值、不更新 `g_pkt`。**并且把耗时打印出来**——
"预算 200 ms"不能只是注释里的一句话：

```
[bt] SELFTEST sample took 2 ms (budget 200 ms)
[bt] SELFTEST decode ax=-23 ay=35 az=-1011 mg |a|=1012 mg
[bt] SELFTEST PASS (fails=0)
```

**如实说明**：2 ms 是"传感器有可读样本"时的实测（正常情况第一次就成）；
预算是给"拿不到合理样本"的病态情况兜底的，且**下界仍是单次 oneshot 的量级
（~160 ms）**——那部分没法从外面切断。本轮只保证"不会因为重试而累加到 640 ms"。

### 11.2h 断线后会不会自动重开广播 —— ❌ 结论被空口实测推翻（2026-09-18 晚订正）

B3 现场最怕的是"手机连了一次、断开后再也搜不到"——那 demo 就变成一次性的。
查了 zblue 的广播状态机，结论是**会自动重开**：

| 环节 | 位置 | 事实 |
|---|---|---|
| 持久标志 | `host/adv.c:1115` | `atomic_set_bit_to(adv->flags, BT_ADV_PERSIST, !dir_adv && !(param->options & _BT_LE_ADV_OPT_ONE_TIME))` |
| 我们的参数 | `pw_btgatt.c` | `BT_LE_ADV_CONN` = `BT_LE_ADV_PARAM(BT_LE_ADV_OPT_CONNECTABLE, …)`，peer = NULL ⇒ `dir_adv = false`，且**没有** `ONE_TIME` ⇒ **`BT_ADV_PERSIST = true`** |
| resume 条件 | `host/adv.c:1509` `bt_le_adv_resume()` | 要求 `BT_ADV_PERSIST && !BT_ADV_ENABLED` 且 `BT_ADV_CONNECTABLE` ⇒ 我们全满足，于是执行 `bt_le_adv_set_enable(adv, true)` |
| 触发点 | `host/conn.c:1576` | 外设侧 LE 连接对象被 **deallocated**（即断开后）时调用 `bt_le_adv_resume(hdev)`（需 `CONFIG_BT_PERIPHERAL`，本板 `=1` 已开） |

**当时的结论**：手机断开后广播会自动恢复，可以反复连，不需要复位板子。
**如实标注**：这一条是**读源码得出**的，没有经过空口实测。

#### ⚠️ 2026-09-18 晚订正：实测推翻了这个结论

用户报"手表连着之后，蓝牙断开很久了还显示已连接"，顺着查蓝牙链路时做了空口实测：

```
① BlueZ 主动断开              → Device1.Disconnect() 返回成功
② BlueZ 侧属性                → Connected=False
③ 清掉 BlueZ 的缓存设备对象后再扫描 15 s
   → 扫到 13 个别的设备，**没有 PhyWear** ⇒ 手表**没有重新广播**
```

也就是说：**断开之后手表就搜不到了，必须复位板子（或重跑 `phywear cap bt`）才能重连。**
上面那张"代码级推导"表每一步都能对上源码，但**实际结果不成立** —— 推导里少考虑的是
`bt_le_adv_resume()` 的前置条件（要求 `BT_ADV_PERSIST && !BT_ADV_ENABLED`，
连接期间 legacy adv 是被 *暂停* 而不是 *禁用*，`BT_ADV_ENABLED` 未必像推导假设的那样被清掉），
以及 resume 失败时**没有任何日志**（这条链本来就是"静默失败"）。

顺带纠正另一处我自己的错误推断：我曾用"`.config` 里 `CONFIG_BT_ADV_PERSIST` 计数为 0"
当作"持久广播没开"，进而怀疑文档写错了 —— **这个 Kconfig 符号在 zblue 里根本不存在**
（`BT_ADV_PERSIST` 只是 `hci_core.h` 里的一个运行时标志位），所以那个计数毫无意义。
**教训**：`grep` 不到一个符号，只能说明"这个符号不在配置里"，不能推断"这个特性没编译进去"。

**修法（本轮已改，待真机复验）**：不再依赖那套自动 resume，在 `pw_disconnected()` 里
**显式**投一个工作项 `pw_adv_restart()`，断开后重新 `bt_le_adv_start(BT_LE_ADV_CONN, …)`，
并**打一行 rc**：

```
[bt] adv restart rc=0 (ok)        ← 期望
```

为什么用工作项而不是在回调里直接开：回调在连接拆除**过程中**执行，那里立刻重开广播
容易撞上还没释放完的广播实例；投到系统工作队列上更稳。

### 11.2i 第七轮：一键验收脚本 + 它当场抓到的两个"测量口径"问题

逐项打 PASS/FAIL 并落盘 sha256。实测 **15/15 全过**（`docs/evidence/accept-20260918/`）：

```

PASS  B2b SELFTEST PASS / |a|=1020 mg / sample took 2 ms / 无 RX 读错误
```

**但它第一次跑就"失败"了两项，而这两次都是我的**测量方法**有问题，不是设备坏了** ——
两条都值得记下来：

**① 帧率是"窗口量"，命令发出时刻决定读数（口径陷阱）**
`[phywear] alive t=30s loops/s=… fps=…` 里的 `fps = 本窗口实际推屏帧数 / 30`，
窗口从 GUI 启动起算。脚本第一版在复位后多静置了 3 s 才发命令，于是窗口整体后移：

| 命令发出时刻 | 观测 | 可重复性 |
|---|---|---|
| 复位后 **t≈3 s**（历史基线口径） | `loops/s=204 fps=12` | 连测 4 次一致 |
| 复位后 **t≈6 s**（脚本第一版） | `loops/s=183 fps=11` | 连测 4 次一致 |

**⇒ 比较帧率必须固定"命令发出时刻"**，否则会把口径差当成性能退化。
脚本已改回 0.5 s（同一口径），并把"最多测 3 次、有一次达标即 PASS"作为保险。

**② 串口是并发写，"证据没抓到" ≠ "功能失败"**
诊断这一项时抓到一次自检输出被冲掉：`read sensor -> 16 B` 与 `decode …` 两行整行消失，
只剩半行 `[bt] St" ->`。而**功能是好的**（同一段里 `SELFTEST PASS` 照常打印）。
原因是 phywear 的 `printf` 与 ai_agent 的 `syslog` 同时在写同一个控制台。
脚本第一版因此把一个正则没匹配到判成 `|a|=0 mg` **FAIL** —— 这是**假失败**。
已改成：B 阶段缺任一证据就重采（最多 3 次），**绝不把"没抓到证据"当成"功能失败"**。

### 11.2j 第八轮：给 B3 判定器补"正方向"自测（此前只测过"没手机"的方向）

`pw_bt_b3.py` 原来**只在"没有手机"的方向上做过负对照**。万一手机那边一切正常、
而脚本的正则/区间写错，人就会看到**假 FAIL**、以为设备坏了 —— 这个方向一直没测过。

### 11.2l 第十轮：把"服务到底注册上没有"也证下来（句柄结构自检）

此前自检只 dump 了 UUID 与权限 —— **那证明不了服务真的注册成功**：`handle` 是
`bt_gatt_service_register()` 在**注册时**才写进属性的；若注册没生效，handle 会是 0，
手机来的 ATT 请求会**全部找不到东西**，而日志上"UUID/权限都对"看不出任何异常。

自检因此加 ①b 步：dump 每个属性的 `handle`，并断言两条结构不变量：

```
[bt] SELFTEST attr[0] handle=0x000e 2800 perm=0x01 read=Y write=-
[bt] SELFTEST attr[1] handle=0x000f 2803 perm=0x01 read=Y write=-
[bt] SELFTEST attr[2] handle=0x0010 e0f1a001-… perm=0x01 read=Y
[bt] SELFTEST attr[3] handle=0x0011 2902 perm=0x03 read=Y write=Y
[bt] SELFTEST attr[4] handle=0x0012 2803 perm=0x01 read=Y write=-
[bt] SELFTEST attr[5] handle=0x0013 e0f1a002-… perm=0x02 write=Y
[bt] SELFTEST handles: value=0x0010 ccc=0x0011 (ccc 应为 value+1)
```

① **所有 handle ≠ 0** ⇒ 服务确实注册进了 ATT 数据库；
② **CCC 紧跟在特征值后面**（`ccc == value + 1`）⇒ 这正是 zblue 通知路径的前提：
它用 `bt_gatt_attr_value_handle()` 取值句柄、再据它找到对应的 CCC。

顺带产出一张**给 B3 用的句柄对照表**（已写进 §11.2 的 B3 步骤）：手机 App 里
Sensor 值应是 `0x0010`、它的 CCC 是 `0x0011`、Command 值是 `0x0013` ——
对不上就说明连错服务了。验收项 **16 → 18**，实测 **18/18 全过**。

### 11.3 任务 3（网络 N1→N2）—— ❌ **被硬件缺失阻断，不是软件问题**

| 证据 | 内容 |

| **运行时终判（最强证据）** | 在 `nsh>` 执行 `ifconfig` → **`ifconfig: open failed: 2`**（ENOENT：命令在、网卡不在）。`help` 里 `ifconfig / ifup / ifdown / arp / nslookup` **都注册了** ⇒ netutils 编进来了，只是没有任何 netdev 可打开。全文里 `wlan` / `eth0` / `Link encap` / `inet addr` 出现次数均为 **0**（`15_n1-no-netdev-runtime.log`） |

**结论（2026-09-18 第二次修正，重要）**：

1. **WiFi 路径确实不可达**：本板没有无线网卡，`set_wifi`（内部 `ifup wlan0` + `wapi`）无从执行。
2. **但"让手表拿到 IP、把数据发到宿主"本身可以做** —— 换一条**不需要网卡**的链路：
   **SoC USB 设备口 → CDC-ACM → SLIP**。依据：
   - 板级 pinmux `bsp_pinmux.c:178-179` 把 `PAD_PA35/36` 配成 **USB_DP/USB_DM**；
   - 板级 `sifli_ap.c:693` 已 `cdcacm_initialize(0, NULL)`，板上有 `/dev/ttyACM0`；
   - `nuttx/drivers/net/slip.c` 本来就在树里，`slip_initialize()` 是公开 API
     （`nuttx/include/nuttx/net/slip.h:101`），只差 `CONFIG_NET_SLIP=y`。

   **软件这一侧本轮已补齐并实测**：defconfig 加 `CONFIG_NET_SLIP=y` + `CONFIG_NETUTILS_DHCPC=y`，
   新增 `phywear net`（`pw_net.c`）调 `slip_initialize(0, "/dev/ttyACM0")`。实测：

   ```
   [net] 本板无无线网卡（ifconfig: open failed: 2 = ENOENT）⇒ set_wifi 不可达
   [net] 改走 USB CDC-ACM + SLIP：slip_initialize(0, /dev/ttyACM0)
   [net] slip_initialize rc=-107 (FAILED)
   ```

   `-107 = -ENOTCONN`，**根因已定位**：`slip_initialize()` 只可能在 `file_open()`
   失败时返回错，而 `file_open("/dev/ttyACM0")` 被 cdcacm 拒了 ——
   `nuttx/drivers/usbdev/cdcacm.c:2140`：`if (priv->config == CDCACM_CONFIGIDNONE)
   return -ENOTCONN;`（注释就叫 `SETUPNOTCONNECTED`）。
   ⇒ **板的 USB 设备口没有被任何 USB 主机枚举**（宿主机 `lsusb` 里只有 CH340
   `1a86:7523`，没有 `38F4`）。

   **所以只差一根 USB 数据线**（把表的 USB 数据口插到本机）：
   ```
   # 板子侧
   phywear net                      # 期望变成 rc=0，sl0 注册成功
   ifconfig                         # 应出现 sl0
   ifconfig sl0 192.168.7.2         # 先静态验证 IP 层通
   # 宿主侧（对端）
   sudo slattach -p slip -s 115200 /dev/ttyACM0 &
   sudo ifconfig sl0 192.168.7.1 pointopoint 192.168.7.2 up
   # 板子侧再 renew sl0 走 DHCP（宿主起 dhcpd 或 dnsmasq）
   ```
   插上线以后，我就能把这条链路一路验到 TCP（`ping` / 一个小 UDP 发送）——
   那才是真正意义上的 **N1（拿到 IP）+ N2（测量数据发宿主）**。

**不允许把未实测写成已通过**：上面标注"期望 rc=0"的部分**尚未实测**，因为线还没插。

**2026-09-18 最终结论（经用户确认）**：用户确认**无法把表的 USB 数据口插到宿主**
（愿意装 `net-tools` / 用 PPP，但缺的是**物理链路**，不是宿主软件）。因此在本板现有条件下：

| 路径 | 状态 |
|---|---|
| WiFi（`set_wifi` → DHCP） | ❌ 硬件不可达（本板无无线网卡）—— **已证** |
| USB CDC-ACM + SLIP | 🔶 软件五环齐备、失败模式可一行判别，但**缺一根 USB 数据线** —— 链路不通 |
| PPP（宿主已有 pppd） | 🔶 同上：宿主侧无需安装，但同样需要那条 USB 数据链路；板子侧还要开 `NETUTILS_PPPD` |

⇒ **任务 3 的 N1/N2 在本板 + 现有接线条件下无法收尾**，如实计入「已知限制」。
若将来能接上表的 USB 数据口，`docs/07 §5.0b` 里的步骤可直接照做（届时只需把
`phywear net` 的 `rc=-107` 变成 `rc=0`，再配宿主 `slattach`/`pppd`）。

**可以部分替代 N2 的路径（已交付，待人工确认）**：N2 的措辞是「测量数据/Agent 消息
发宿主或局域网端点」。B2 的 sensor 特征 + Notify 已经做到「**测量数据实时发到宿主

**定位手段**：把 `h4.c` 的 `PW_H4_TRACE` 打开，再用新写的
`tools/phywear/pw_h4_notify_decode.py` 把 `[H4] TX` 按
HCI ACL → L2CAP(CID 0x0004=ATT) → ATT 逐层拆开：

```
修复前：02 01 00 17 00 13 00 04 00 1b 00 00 e7 ff 27 00 …
                                  ↑op=Notify  ↑value_handle = 0x0000  ❌
修复后：02 01 00 17 00 13 00 04 00 1b 10 00 e7 ff 27 00 …
                                             ↑value_handle = 0x0010  ✅
```

| | 订阅窗口内通知帧 | value handle | 宿主侧收到 |
|---|---|---|---|
| 修复前 | 56 | **0x0000 × 56** | **0 个包** |
| 修复后 | 2 | 0x0010 × 2 | **2 个包** ✅ |

BlueZ 收到句柄 0x0000 的通知，找不到对应特征，**静默丢弃** —— 所以设备侧
日志看不出任何异常。这类"只在空口上看得见"的 bug，只能靠字节级 trace + 分层解码。

**代码级根因**：`external/zblue/zblue/subsys/bluetooth/host/gatt.c`

上游 Zephyr 在 `bt_gatt_notify_cb()` 里 `conn == NULL` 时是**就地**在已经填好
`data.handle` 的 `struct notify_data` 上做 CCC 遍历：

```c
	data.handle = bt_gatt_attr_get_handle(data.attr);
	...
	bt_gatt_foreach_attr_type(data.handle, 0xffff, BT_UUID_GATT_CCC, NULL,
				  1, notify_cb, &data);
```

zblue 为支持多控制器把它抽成了独立函数 `gatt_notify_mc(uint16_t handle, …)`，
新函数里 `struct notify_data data = { 0 };` **把句柄丢了**，而 `notify_cb()`
取的正是 `data->handle`（用来填 ATT PDU 的 handle 字段）⇒ 恒为 0。
`gatt_indicate_mc()` 同一个毛病。

**修复**（两行，语义与上游完全一致）：

```c
 static int gatt_notify_mc(uint16_t handle, struct bt_gatt_notify_params *params)
 {
 	struct notify_data data = { 0 };
 	...
 	data.nfy_params = params;
+	data.handle = handle;
```

### 13.2 唯一的硬约束：跨线程

连接/断开/CCC/写特征这些回调跑在 **Zephyr 系统工作队列**线程上，而界面在
**phywear 主线程**上。所以：

* BT 回调里**绝不调用 LVGL** —— 那是跨线程碰渲染器，必崩，而且崩在连接那一刻
  （最像"蓝牙自己坏了"，最难查）；
* 回调只写 `g_link`（`pw_btgatt.c` 里的 `struct pw_bt_link_s`：连接标志、订阅标志、
  MTU、收发计数、10 行环形日志、`seq`）；
* 界面只读 `pw_bt_link()`，并且只在 `lv_timer` 回调里改控件（主页点 250 ms、
  蓝牙页 300 ms）；
* 两边**都不加锁**：字段都是单字宽读写，日志用 `seq` 标定有效性；最坏情况 UI 读到
  一行"写到一半"的文本，下一次刷新自我修正。为这个在 HCI 回调里拿互斥量是不划算的
  （射频事件路径上引入阻塞可能丢包）。

这层约定写在 `pw_btgatt.h` 顶部，UI 与 BT 两侧的注释都指向它。

### 13.3 空口连通性测试：为什么判据是"收到 echo"而不是"写成功"

宿主侧 `tools/phywear/pw_ble_central.py --text-test`：

```
PASS  找到 text 特征 …a003
PASS  读 …a003 得到状态串      PhyWear bt conn=1 sub=0 rx=1 tx=0 echo=0 mtu=23
PASS  写文本后收到设备 echo（双向连通）  写 'hello-1789723972' → 收到 ['echo: hello-1789723972']
PASS  echo 内容与所写一致      echo: hello-1789723972
```

BlueZ 的 `WriteValue` 返回成功**只说明本地协议栈把包发出去了** —— 空口丢没丢、
设备收没收到、设备能不能主动发回来，它一概不知道。收到原样 echo 才同时证明
「手机→手表」与「手表→手机」两个方向都通。这与 B3 那次"设备侧 rc=0 连打 56 条、
宿主一个包都收不到"是同一类教训：**要验的是对端真的收到了**。

设备侧判据（`pw_bt_b3.py --central --text`，8 项）里，`[bt] msg in` 与 `[bt] echo tx`
都限定在"已连接之后"—— 因为设备侧自检自己也会往文本特征写一条 `selftest`，
用全量日志去找会把自检那条误算成手机写的（就是 §11.2c 那个假 PASS 的同一类错误）。

### 13.6c 用户报「断开很久了还显示已连接」—— 根因与修复（2026-09-18 深夜）

用户原话："手表端的，链接蓝牙之后，即使蓝牙断开很久了，还是显示已连接。"

**两件事，先说我自己的锅。**

#### ① 主因：桌面测试工具测完从不断开，手表一直是对的

`pw_ble_central.py` 测完直接退出，**而 BlueZ 是中心设备、进程退出并不会断开 LE 链路**。
所以链路一直挂着，手表（外设侧）的 `connected` 就一直是真 —— 显示"已连接"**完全正确**。
实测现场：17:58 那次桌面测试跑完，18:0x BlueZ 仍报
`dev_5A_58_62_96_E7_57 Connected=True ServicesResolved=True`。

用户把"关掉测试窗口"理解成"蓝牙断开了"，而手表看到的是一条**真实存在**的链路。

> **教训（值得单独记）**：遇到"设备显示和用户预期不一致"，**先怀疑测试工具，别先怀疑固件**。
> 这次差点去改固件的状态机，而固件从头到尾没错。

**修法**：`run_full_test()` 收尾显式 `Device1.Disconnect()`，并作为一条判定项
（`PASS 测完主动断开（手表回到可被发现）`）；CLI 加 `--keep-connected`，
GUI 加「测完保持连接」勾选框。

#### ② 顺带查出的真 bug：断开后手表**再也不会广播**（搜不到、连不上）

查①的过程做了空口实测，结果**推翻了我自己在 §11.2h 里"读源码得出"的结论**：

```
① Device1.Disconnect() 成功，BlueZ 侧 Connected=False
② 清掉 BlueZ 缓存对象后扫 15 s → 扫到 13 个别的设备，没有 PhyWear
③ 设备侧串口原文：直接 bt_le_adv_start() 回 -114 = -EALREADY
```

根因：链路建立时**控制器自己**把 legacy 广播停了，但 host 侧的 `BT_ADV_ENABLED`
标志位**没被清掉**（`adv.c` 在该位为 1 时直接 `return -EALREADY`）。
而内置 `bt_le_adv_resume()` 的前置条件是 `BT_ADV_PERSIST && !BT_ADV_ENABLED`
—— 第二个条件永远为假 ⇒ **resume 永不生效，断开后设备再也搜不到**（要复位板子才能重连）。
这是个**静默失败**：没有任何日志。

**修法**：`pw_disconnected()` 里投工作项，遇 `-EALREADY` 先 `bt_le_adv_stop()`
清标志位再 `bt_le_adv_start()`，两个 rc 都打日志。实测：

```
   25.379  [bt] B3 disconnected: 04:EC:D8:F3:73:8D (public) reason=0x13
   25.379  [bt] adv busy(EALREADY), stop rc=0, retry start
   25.379  [bt] adv restart rc=0 (ok)
```

`reason=0x13` = remote user terminated ⇒ **断连回调本来就触发**，
手表端"状态翻转"这条路一直是通的（问题从来不在它）。

蓝牙页状态走 `btp_tick`(300 ms) —— 必须各证一遍，不能互相代替。

#### ④ 为此加的两个取证入口

`phywear shot <page>` 是"开机后第一个 GUI"，拍完就退出、**BT 栈随进程消失**
（实测：shot 跑完板子回到 `nsh>`，此时不广播）。所以没法"先连一次、再重启、再拍照"。
于是加了两拍等待：`btafter`（主页）与 `btlog`（蓝牙页），语义都是
**等连上 → 再等断开 → 静默 4 s → 出图**。

### 13.6d 链路层优化尝试：ATT MTU（修好了）+ 连接参数（实测无效）

**动机**：任务 3 唯一剩下的物理通路是 BLE，而 BLE 要当"网络承载"就必须先把链路
参数摸清、把 MTU 拉起来。所以先做这两件事，并且**必须先量基线**再改。

**新增测量方法**（`pw_ble_central.py --perf`）：往 `…a003` 写一条短文本、
等设备把 `echo:` 发回来 —— 这是**应用层往返**，设备侧是立刻回 echo 的，
所以基本等于"连接间隔 × 往返跳数"。同配置重复测的抖动只有 **±1 ms**，
因此这个尺子足以判定改动有没有用。

| 配置 | 设备上报 | 往返延迟 中位 (ms) | 定长吞吐 (条/s) |
|---|---|---|---|
| **优化前固件** | `mtu=23`（快照假值） | **135.0** | 7.3 |
| 连接参数请求 **ON** | `mtu=517 itv=24 lat=0 sto=400` | 89.5 | 9.9 |
| 连接参数请求 **OFF** | **同上，完全一致** | 90.5 / 91.1 / 91.3 | 11.1 |
| MTU 交换也 **OFF** | **仍是 `mtu=517`** | 91.0 | 10.8 |
| 宿主适配器断电重启后 | `mtu=517 itv=24` | 90.1 | — |

**三件结论**：

1. ✅ **真 bug 已修**：`MTU 23` 是连接瞬间的快照。注册 `bt_gatt_cb.att_mtu_updated`
   后显示真实协商值 **517**（tx=517/rx=253）；手表页现在是
   `MTU 517 · 30.0 ms`（见 `docs/evidence/bt-linkopt-20260918/btlink_mtu_interval.png`）。
2. ❌ **连接参数请求对 BlueZ 是 no-op**：ON/OFF 三次，`itv/lat/sto` 与延迟同水平。
   背景：连接参数由**中心设备**决定，外设只能发请求。
3. ⚠️ **135→90 ms 是真的（方差极小）但归因不明**：关掉 MTU 交换后 MTU 仍是 517
   （BlueZ 自己会交换）⇒ 也不是 MTU 的功劳。**所以不把它算作本次优化的收益**，
   如实留成待解释的差异。

**另一条教训**：`bt_conn_cb.le_param_updated` 在这条链路上**从未触发**
（串口里一行都没有）。只看它就会永远不知道真实连接间隔 —— 改成在周期工作里
用 `bt_conn_get_info()` 查实时值（BT 工作队列线程上，与"回调里不碰 LVGL"同一条纪律）。

**下一次真正可能改善延迟的是** `2M PHY` 与 `Data Length Extension`
（直接减少空口时间）—— 连接间隔在 BlueZ 下动不了。动手前先读控制器能力
（`Read Local Supported Features`），别白做一轮。

### 13.6e 任务 3 第三条路线：PPP over BLE —— **端到端打通**（N1/N2 达成）

**动机**：本板没有无线网卡、USB 数据线又插不上 ⇒ BLE 是唯一现成的物理通路。
BNEP/蓝牙 PAN **不可行**（zblue 与 NuttX 都没有 BNEP 实现，且要 BR/EDR）；
6LoWPAN-over-BLE 设备侧要自己写头压缩+分片（重，且 IPv6-only）；
**PPP 最划算** —— 设备侧 `apps/netutils/pppd` 就在树里、宿主侧 `pppd` 也早已安装，
只差一条"BLE ↔ 伪终端(pty)"的字节管道。

#### 13.6e.1 先把 SRAM 墙拆掉（这是 09-18 那轮唯一的卡点）

上一轮（`docs/evidence/bt-ppp-20260918/`）结论是"功能跑通但装不进 SRAM：余量 4~5 KB、
需求 ~18 KB"。这次先审 SRAM 大户（`arm-none-eabi-nm --print-size --size-sort` 按地址区间筛），
发现两笔**白占的**：

| 项 | 大小 | 说明 |
|---|---|---|
| `g_hp_work_stack` / `g_lp_work_stack` | 16,096 B × 2 | NuttX 的 hpwork/lpwork 栈。它们**没有任何显式配置**，只是继承了板级 `CONFIG_DEFAULT_TASK_STACKSIZE=16096`（NuttX 默认只有 2 KB） |
| PPP 的两个任务栈 | 2,048 + 16,384 B | 用 `K_THREAD_STACK_DEFINE` 静态占 SRAM，可改用**堆**（本板堆在 PSRAM，空闲 7.3 MB） |

改完实测（全部真机烧录 + 复位实测、构建输出为证）：

| 配置 | SRAM | 变化 |
|---|---|---|
| 改动前（PPP 关，出货态） | 496,452 B（94.69%） | 基准 |
| `CONFIG_SCHED_HPWORKSTACKSIZE=8192` + `LPWORKSTACKSIZE=8192` | **480,644 B（91.68%）** | **−15,808 B** |
| 再把 PPP 两个任务栈改从堆上要 + 打开 PPP（`PW_BT_PPP=1` + 5 行 CONFIG） | **483,316 B（92.19%）** | 净比基准 **低 13,136 B** |

⇒ 结论：**"SRAM 墙"其实是两个从没被有意识配过的默认值**。之前记的"本板悬崖
96.76% 挂死 / 95.98% 能起"依然成立，只是现在根本用不到那里了。

8 KB 的 workqueue 栈**安全性是用完整负载验的**（不是"看起来够"）：
一键验收 18/18（含 BT 服务端自检 + 采样 + 浸泡 60 s）、
宿主当中心设备的 B3 文本往返（设备侧 8/8 + 宿主侧 9/9，`echo: hello-…` 双向成立）、
GUI 主页截图 sha256 与金标 `e356689d…` **逐字节相同**、帧率 **12 不变**。
证据另有 `docs/evidence/ws-stack-20260918/`。

本固件里跑在 hpwork 上的只有两个 worker：BT 的 HCI 接收
（`sf32lb52_bt_adapter.c`）与触摸屏（`ft6146.c`，`CONFIG_INPUT_FT6146=y`、IRQ pin 41）。
前者用 B3 双向文本压满验证；**后者（触摸）自动化脚本造不出真实触摸事件，已于
2026-09-18 深夜由用户现场在屏上点按确认"未发现异常"**（同一 boot 心跳打到 `t=240s`、
无 panic/断言/复位）—— 人工确认文本见 `docs/evidence/ws-stack-20260918/HUMAN-touch-confirm.md`
（那里也写明了这条确认的边界：它是"点按后设备继续运行"，不是栈高水位数字）。

#### 13.6e.2 做出来的东西

* 设备侧 `apps/examples/phywear/pw_btppp.c`：第二个 GATT 服务做**字节管道**
  （`…a101` 写 = 主机→设备，`…a102` 通知 = 设备→主机，同一条特征还能读**状态串**：
  `up/sub/slave/rx/tx/drop/ptx/prx/pppd`）。一个任务建 pty（SUSv1）并与环形缓冲对搬，
  另一个任务跑**真正的 NuttX pppd**（`connect_script=NULL`，pty 直连没有 AT 猫可拨）。
* 宿主侧 `tools/phywear/pw_bt_ppp.py` 现在有三种模式：
  **`--peer`（自己当 PPP 对端：LCP+IPCP+ICMP，不需要 root）**、默认（桥到 PTY 交给内核 `pppd`）、
  `--sniff`（只解帧）。配套 `tools/phywear/pw_ppp_frame.py` 是最小 HDLC/FCS 组帧解析器。
* `tools/phywear/pw_bt_ppp_e2e.py`：一条命令跑完整个验收（复位 → 后台起 PPP →
  起宿主对端 → 在设备上跑 `ifconfig`/`ping` → 落盘串口原文 + 宿主日志 + SHA256SUMS）。
  判定器自身也有自测：`pw_ppp_frame.py --selftest` 8 项、`pw_bt_ppp.py --selftest` 7 项（含负对照）。

#### 13.6e.3 实测结果（证据 `docs/evidence/bt-ppp-e2e-20260918/`）

设备侧串口原文（`dev.log`）：

```
[ppp] bridge task up (stack 8192 B, from heap)
[ppp] pty master fd=4 slave=/dev/pts/0
[ppp] pty 已设 raw（master+slave 两侧）slave fd=5
[ppp] 主机订阅状态 sub=1（等了 9 s）→ 拉起 pppd
[ppp] starting pppd on /dev/pts/0
[netmgr] Found iface ppp0 addr 192.168.7.2
ifconfig
ppp0	Link encap:TUN at RUNNING mtu 296
	inet addr:192.168.7.2 DRaddr:192.168.7.1 Mask:0.0.0.0

```

宿主对端（`host.log`）看到完整的 LCP + IPCP：`★ LCP UP` → `★ IPCP UP`，
并且给设备发的 `IP-Address=0.0.0.0` 回了 **Configure-Nak(192.168.7.2)**。
`pw_bt_ppp_e2e.py` 判定 **6/6**（ppp0 建好 / RUNNING / 拿到 IP / LCP UP / IPCP UP / ping 有回包）。

**为什么宿主是"用户态对端"而不是内核 pppd**：内核 `pppd` 要建网络接口、必须 root，
本机 `sudo` 需要密码。所以验收走用户态对端；要用真正的宿主接口仍然可以
（`pw_bt_ppp.py` 桥模式 + `sudo pppd /dev/pts/N …`，见证据 README §4）。

#### 13.6e.4 这一轮真正踩到的 7 个坑（都已进 docs/07 坑 37–43）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 打印完 `starting pppd` 后整机静默 | `phywear` 主任务 `return 0` ⇒ **task_group 被销毁**，桥/pppd 两个 pthread（zblue 的 `k_thread_create` 就是 `pthread_create`）一起消失 | 入口**不返回**，用 `phywear btppp &` 后台跑 |
| 2 | 设备侧一直 `notify FAILED rc=-22` | 通知发给了 `attrs[2]`（**rx 值**，只有 WRITE、没有 NOTIFY）⇒ EINVAL；正确是 `attrs[4]`（`BT_GATT_CHARACTERISTIC` 展开成"声明+值"两条） | `PW_PPP_ATTR_TX 2 → 4` |
| 3 | pppd 一个字节也读不到主机发的帧 | NuttX pty 默认是**终端**语义（master `OPOST\|OCRNL`、slave `OPOST\|ONLCR` + `ECHO\|ICANON`）⇒ ICANON 按行缓存，HDLC 帧里没有换行符 | master/slave 两侧都设 raw |
| 4 | `write(pty master)` 回 `errno=32 (EPIPE)` | 对端还没有开着的 slave fd 时写不进去（`pppd()` 也因此只回一个光秃秃的 `2`） | 桥自己开一个 slave fd 并**一直开着**（只持不读，不抢数据） |
| 5 | 桥任务第一次 `write(pty)` 之后静默 | 桥栈 2048 B 不够，栈溢出**没有 panic** | 两个任务的栈改成从**堆**上要（8192 / 16384） |
| 6 | pppd 一行都跑不出来、`ppp0` 都没建 | ① 本端口 `K_PRIO_PREEMPT(x) = CONFIG_NUM_COOP_PRIORITIES + x`，而 **NuttX 数值越大越紧急** ⇒ 桥(109) 反而压过 pppd(108)；② slave 未开时 `poll()` 因 HUP 立刻返回 ⇒ 桥变满速死循环 | 桥压到 106（低于 pppd）+ 空转 `usleep(2 ms)` 兜底 |
| 7 | `nsh: ping: command not found` | 两个 ping 应用一个都没编进来 | defconfig 加 `CONFIG_SYSTEM_PING=y` |

**一处误判纠正**：09-18 那轮把"pppd 之后无声"归因为 **"pppd 栈不足 → 硬故障 → 看门狗复位"**，
那是**没有对照的猜测**（当时 `phywear btppp` 直接 `return 0`）。真因是上面的坑 1（task_group 生命周期）。
这次把入口改成不返回之后，同样 16 KB 的 pppd 栈跑得好好的。

#### 13.6e.5 出货态

PPP **默认开着**（`PW_BT_PPP=1` + defconfig 5 行 CONFIG 使能）：
flash **2,576,888 B（15.36%）**、SRAM **483,316 B（92.19%）**，比做 PPP 之前的
出货态（496,452 B）还低 13 KB。`phywear btppp` 是"用才付"的：
GATT 服务与 pty 只在跑该子命令时创建，两个任务栈从堆上要。

**顺带查清一个长期被误判的坑**：加这些 CONFIG 时 `resetconfig` 报了项目里反复出现的
`nuttx_export_kconfig_by_value() ... REGEX ... needs at least 5 arguments`。
项目记忆把它归因为"手改 `.config`"——**真因是我在 defconfig 里加了含半角空格的中文注释**。
最小复现（`cmake -P`，5 用例）见证据目录 `bt-ppp-20260918/plain|ascii|spaces|nospace|symbols`：

| 注释 | 结果 |
|---|---|
| 纯中文（全角标点，无半角空格） | ✅ |
| 纯 ASCII | ✅ |
| 中文 + 半角空格 | ❌ 触发 |
| 框线 `──` / 箭头 `↔ ⇒` / 破折号 `——` | ❌ 触发 |

⇒ **defconfig 里含非 ASCII 的注释行不要出现半角空格，也别用框线/箭头类符号。**
