# 11 · 面板时序与 VSYNC 方案（待批 · 未动工）

> **本轮性质：只读调研 + 方案，未改任何一行代码、未烧录。**
> 前置结论来自 P0 三轮实测（`docs/03 §4.12`、`docs/evidence/p0-20260916/`、`docs/evidence/lvbench-20260916/`）：
> 软件侧五个假设全部被实测否决，本队页面在数据连续变化时跑到 **48~49 FPS**，
> 而**轻负载上限实测 56~63 FPS**（LVGL 官方跑分：Empty screen 56、Single rectangle 63）。
> 也就是说：**软件侧已经贴着固有帧节拍了，再往上只能动面板级配置。**

## 1. 现状取证（全部有文件行号）

| 项 | 现状 | 出处 |
|---|---|---|
| 面板/接口 | CO5300，QAD SPI（4 数据线），RGB565 | `co5300.c:116` `.lcd_itf = LCDC_INTF_SPI_DCX_4DATA` |
| 总线时钟 | **50 MHz**（`LCD_MAX_CLK_FREQ` 全仓未定义 → 走回退值）；注释写明 "CO5300 RGB565 only support 50000000" | `co5300.c:120-126` |
| 理论带宽 | `freq << 2` = 200 Mbit/s = **25 MB/s** | `drv_lcd.c:1383-1388` |
| **VSYNC/TE** | **配置想开、代码实际关着（死代码）** | 见 §1.1 |
| 帧率控制寄存器 | 初始化表**没有**写任何帧率控制寄存器（全表只有 0x01/0xF4/0xF5/0xFE/0xC4/0x3A/0x35|0x34/0x20/0x51/0x53/0x2A/0x2B/0x11/0x29 与亮度） | `co5300.c:200-300` |
| 实测帧节拍 | 16~18 ms（空屏 56 FPS、单矩形 63 FPS、本队页面单帧窗口 17.1 ms） | `docs/evidence/lvbench-20260916/` |

### 1.1 【新发现】VSYNC/TE 是死代码：宏前缀不匹配

- Kconfig：`LCD_USING_CO5300` 下 `config LCD_CO5300_VSYNC_ENABLE` 是 **`def_bool y`**（`vendor/sifli/boards/sf32lb52/drivers/lcd/Kconfig:79`）
  ⇒ 构建产物里是 **`#define CONFIG_LCD_CO5300_VSYNC_ENABLE 1`**（`cmake_out/.../include/nuttx/config.h:374`，实测 grep 确认）。
- 但驱动代码判断的是 **不带前缀**的名字：
  - `co5300.c:132-137`：`.syn_mode = HAL_LCDC_SYNC_VER` 在 `#ifdef LCD_CO5300_VSYNC_ENABLE` 内 → **实际编译成 `HAL_LCDC_SYNC_DISABLE`**
  - `co5300.c:267-271`：`REG_TEARING_EFFECT_ON` 同样在该宏内 → **实际执行 `REG_TEARING_EFFECT_OFF`（TE 关闭）**
- 全仓 grep：`LCD_CO5300_VSYNC_ENABLE`（裸名）**没有任何 `#define`** ⇒ 两处 `#ifdef` 恒为假。

**结论**：这块板当前**没有开 VSYNC 同步、也没开面板 TE 输出**；防撕裂靠的是 LCDC 逐行完成事件
（`wait_line_valid()`，`drv_lcd_fb.c:255`）—— 属于"近似防撕"。这是**配置与代码不一致**，不是设计如此。

### 1.2 TE 引脚是否有走线：**查不到，需原理图**

板级 pinmux（`vendor/sifli/boards/sf32lb52/sf32lb52_lchspi_ulp/src/*.c`）里**没有任何 TE/VSYNC 引脚配置**；
HAL 侧有能力（`bf0_hal_lcdc.c/h` 有 TE 相关接口），但"面板 TE 线是否接到 SoC"**属硬件问题，代码里看不出来**。
这一点直接决定下面 C 方案的生死。

## 2. 三档候选（按风险从低到高，逐档独立可回退）

### A. 纯测量：先把"面板实际帧率"量出来（零代码改动）

- **做什么**：用 (1) 逻辑分析仪/示波器接 TE 线，或 (2) LCDC 的行完成中断计数，
  测出面板 GRAM 实际扫描率与一帧时间。
- **收益**：把"56~63 FPS 上限"从**推断**变成**实测**；后续任何改动都有对照基准。
- **成本**：需要硬件仪器与一次拆机/接线（**要你或有人动手**）。
- **回退**：无（不改东西）。
- **风险**：无。

### B. 帧率控制寄存器：把面板扫描率抬上去（中风险，收益上限最高）

- **做什么**：在 `co5300.c` 初始化表里增加一次寄存器写（通常是帧率控制类寄存器，如 `0xC6`），
  把面板内部 GRAM 扫描率从默认档位提高到 70~90 Hz 档（**具体寄存器地址/位定义必须查 CO5300 数据手册**）。
- **为什么可能有效**：面板扫描率是**独立于 QSPI 总线**的（GRAM 自刷新），QSPI 只承担"脏区写入"，
  所以抬高扫描率**不会**直接受 25 MB/s 带宽限制（当前每帧只传脏区，实测 `flush` 列几乎为 0）。
- **收益上限**：若面板能做到 82 Hz（`co5300.c:139` 的注释提到过 `frame rate=82`，但那是 TODO 注释、**不是实测**），
  天花板有望从 56~63 抬到 70+。
- **风险**：① 超出面板规格可能闪烁/色偏/寿命影响；② 寄存器写错可能花屏（**可通过重烧固件恢复**）；
  ③ 本次网络检索失败，**未能拿到数据手册确认寄存器**——没有手册不建议动手。
- **回退**：删掉那一行寄存器写（一行 diff），或重烧上一版固件。
- **需要你提供**：CO5300 数据手册（或屏幕模组规格书）中"帧率控制"章节。

### C. 打开 VSYNC/TE 同步（高风险，可能黑屏）

- **做什么**：把 `co5300.c` 两处 `#ifdef LCD_CO5300_VSYNC_ENABLE` 改成 `#if defined(CONFIG_LCD_CO5300_VSYNC_ENABLE)`
  （或补一个裸名 `#define`），使 `syn_mode = HAL_LCDC_SYNC_VER` 且打开面板 TE 输出。
- **收益**：严格无撕裂（现在靠行计数近似）；帧节拍与面板严格对齐，**不提高上限**。
- **风险（关键）**：**若面板 TE 线没有接到 SoC，LCDC 会一直等 VSYNC → 屏幕可能不亮/卡死**（§1.2 未证实走线）。
- **回退**：宏改回 `#ifdef`（一行）；**即使黑屏也能救** —— 屏幕不亮不影响串口，
  `flash_with_ftab.sh` 走 sftool 重烧已验证多次（本会话就重烧过 8 次以上）。
- **前置条件（必须先确认其一）**：原理图上 TE 走线 **或** 你先接受"试一次、黑屏就回退"的成本（约 5 分钟）。

## 3. 建议执行顺序与判据

1. **A（零风险）**：先把面板实际帧率量出来 —— 需要你提供仪器/接线条件。
2. **B（等手册）**：拿到 CO5300 数据手册后，我做"单寄存器 + 同口径 A/B"；
   判据：`phywear lvbench` 的 Empty screen/Single rectangle 两项 FPS 是否上抬 ≥10%，
   且**人眼确认无闪烁/无花屏**；不达标即回退。
3. **C（等走线确认）**：确认 TE 走线后再评估；若你同意"试错即回退"，也可先花 5 分钟试一次。

**三档都不改变已交付的观感与功能**；每档都是一行 diff + 一次重烧，回退成本 < 10 分钟。

## 5. 本方案**不**主张什么

- 不主张"提到 82 Hz 就能跑 82 FPS"：帧节拍还受 LCDC/驱动握手影响，**必须实测**。
- 不主张 VSYNC 能提帧率：它只解决撕裂，**不抬上限**，且未证实 TE 走线。
- 不主张当前 48~49 FPS 是缺陷：它已达轻负载上限的 ~82%，属这套硬件+配置的正常区间。
