## A 组：技术原理与选型

**A1. EPIC 硬件加速是官方 PR 给的，那你们在图形链路上到底原创了什么？**
- 答（结论先行）：发动机是官方的，原创在上层取舍与算法路径。我们弃用 lv_chart，自研 pw_scope/pw_graph 的 CPU 光栅加 lv_image 路径，走通 EPIC IMAGE 硬件 blit，真机页面帧率 48–49 FPS（约 82%）。依据 README「工作基础与归属」与 docs/03_技术报告.md，官方来源明确写为 PR #31/#41/#121。
- 追问防备：补一张「官方改动 vs 本队改动」逐文件对照表（src/MANIFEST.md 已有骨架）。

**A2. 物理算法 phyphox 都有现成的，你们自己写 FFT、姿态解算，是不是重复造轮子？**
- 答：不是为写而写，是资源与许可双重约束下的必要自研。FFT、自相关测周期、向心最小二乘都是教科书算法，用纯 C 单精度重实现，未复制其 Kotlin 代码体，SPDX 为 Apache-2.0。依据 app/phywear/NOTICE.md 与 docs/03_技术报告.md 算法章节。
- 追问防备：补一次同输入数据下自研结果与 phyphox 的对照实验（缺数据，需补）。

**A3. 没网没 Key 的「离线意图快路径」，是不是就是写死的 if-else？**
- 答：确实不做端侧大模型推理，这点不装。它的价值是把工具调用留在端侧可用：离线按意图直接执行工具、界面真的切页，有网才走端云。依据 docs/05_AI_Agent与Skill.md 离线降级一节与 docs/evidence/ai-coach-20260913/。我们从不称它为端侧 AI 推理。
- 追问防备：补意图命中率与误触发率实测（缺数据，需补）。

**A4. 真机根本没 WiFi，你们的端云架构是不是纸上谈兵？**
- 答：端云拆分是明确的，但云端在真机上确实没走到，如实认。端侧负责采集、算法、工具与执行；LLM 联调在模拟器实测；真机联网只能走 PPP over BLE，已到 IP 层（设备 ping 3/3、e2e 6/6）。依据 docs/04_应用场景说明.md 与 docs/evidence/bt-ppp-e2e-20260918/。

## B 组：性能与资源

**B1. 你们材料里 39、41、43、48、63 全出现过，到底多少 FPS？**
- 答：承认口径混乱，当场收敛为一套：LVGL 官方 benchmark 全场景平均 39 FPS（CPU 83%、render 22 ms、flush 0）；本队页面 48–49 FPS（约 82%）；主屏刷新率 63，面板 CO5300AF-01 VFR=60 Hz 为物理上限。历史口径一律不外引。依据 docs/evidence/lvbench-20260916/、docs/evidence/p0-20260916/。
- 追问防备：补一页「帧率口径对照卡」，逐个数字写清测量命令与日期。

**B2. 48–49 FPS 是不是专挑好看的页面测出来的？**

- 追问防备：补逐页帧率清单，把最低的页面也列出来（缺数据，需补）。

**B3. SRAM 占到 92.19%，剩下那点余量还敢加功能吗？**
- 答：承认余量紧，这是真实风险。同一构建（md5 41c3377c…）SRAM 483,356 B / 512 KB（92.19%），相减只剩 40,932 B；Flash 倒是宽裕，2,577,592 B / 16 MB（15.36%）。加功能前先做内存预算。依据 docs/09_官方提交模板_填写草稿.md §3.4–3.5（2026-09-18 23:20 构建）。
- 追问防备：补一份新功能内存预算与堆栈水位实测（缺数据，需补）。

**B4. 模拟器才 22–23 FPS，你们的性能是不是全靠那块板子？**
- 答：一半一半，如实讲。真机 40 以上确实依赖官方 EPIC 后端；但同一套 UI/算法层优化让模拟器从很卡升到 22–23 FPS，说明上层取舍本身有效。评委无板时请以代码加实测证据核验，不要拿模拟器数字对标真机。依据 README 性能分层一节、docs/project/fps_timeline.png。

## G 组：续航与可交付性（2026-11-03 补）

**Q21 这块表续航多久？你们怎么测的？**
- 答：电池容量已知（**120 mAh / 3.7 V / 0.444 Wh**，满电**实测 4.24 V**），但续航**未实测** —— 我们没有电流表和库仑计，**不编小时数**。三种可复现测法：① 串一个 USB 电流表读平均电流（最省事，但需改供电）；② 用 `phywear plog` 记两小时电压跌落反推（工具现成，但 3400–4240 mV 线性电量表无放电曲线，误差大）；③ 满电放电到 3.4 V 计时（最接近真实体验，最耗时）。
- 追问防备：**「120 mAh 是不是太小」**→ 这是体积/重量取舍，够不够用靠上面三法实测说话，不拿未测数字宣传；**「为什么不做低功耗模式」**→ 已有自适应休眠（静置态重绘 26/28 → 34/36，+30.8%），本周再补三项动作（见下），收益同样待实测；**「拔掉充电器能跑多久」**→ 当前只能给电压/百分比/充电位实时读数（`phywear power`），小时数等补测后给出，不做口算估算。

**Q21 附：一周内能做的三条省电动作（按性价比，收益均待实测）**
1. 调低 AMOLED 背光亮度、缩短亮屏时长 —— 屏幕是最大耗电项（通用经验，本板未实测）；
2. 静态界面把 VFR 从 60 Hz 降到低刷或直接息屏 —— 与现有自适应休眠互补；
3. 扩大自适应休眠区间、拉长 BLE 连接间隔 —— 需手机端配合。

> 材料里的写法（可直接引）：**「续航：容量已标定（120 mAh / 0.444 Wh，满电 4.24 V），小时数待按既定放电法补测后给出。」** —— 不写小时数，也不写「待补」了事。

## H 组：小米生态与准入（2026-11-04 补）

**Q22 你们和小米生态是什么关系？能进米家 App 吗？**
- 答：硬件与系统层是小米的（黄山派 + openvela），协议层我们已实现小米 MIoT 蓝牙广播（Mi Beacon）：帧与官方文档 v.29 逐字节一致，19 项单测通过，手机可扫到 `0xFE95` 广播。但进米家 App 需在小米 IoT 平台创建产品并通过认证，前提是**企业开发组（营业执照）**；本队无企业主体，因此如实定位为「**技术就绪、准入受限**」，不宣称已接入。
- 追问防备：**「那你们算小米生态产品吗？」**→ 我们是在小米 openvela 与黄山派上完成的作品，向上兼容小米生态的协议能力已具备；剩下的是平台的商业准入流程，不是技术差距。**「为什么不走 Matter？」**→ 本板无 Wi‑Fi/Thread 传输，SRAM 已用 92.19%，CHIP 栈跑不动；且米家对 Matter 设备同样要求认证。**「现在能演示吗？」**→ 能演示广播帧（BLE 扫描器可见 `0xFE95`），不能演示米家 App 添加——那一步会失败，我们不演假。
