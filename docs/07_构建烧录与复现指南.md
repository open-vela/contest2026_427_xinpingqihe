## 2. 构建

### 2.1 真机（立创黄山派 SF32LB52，含 AI Agent）

板级配置：`vendor/sifli/boards/sf32lb52/sf32lb52_lchspi_ulp/configs/nsh-ai`
（= 官方 `nsh` 配置 + `CONFIG_EXAMPLES_AI_AGENT_VELA=y` + 声学 `CONFIG_SF32LB52_SPK=y` 等）

```bash
cd ~/openvela

# 首次、或改过 defconfig 之后：删掉 .config 强制按 defconfig 重新生成
rm -f cmake_out/sf32lb52_lchspi_ulp_nsh_ai/.config
cmake -B cmake_out/sf32lb52_lchspi_ulp_nsh_ai -S nuttx -GNinja \
  -DBOARD_CONFIG=../vendor/sifli/boards/sf32lb52/sf32lb52_lchspi_ulp/configs/nsh-ai \
  -DEXTRA_FLAGS="-Wno-cpp -Wno-deprecated-declarations"

# 日常增量编译
cmake --build cmake_out/sf32lb52_lchspi_ulp_nsh_ai -j16
```

产物：`cmake_out/sf32lb52_lchspi_ulp_nsh_ai/nuttx.bin`（约 **2.03 MB / flash 12%**，SRAM 约 488 KB / 93%）。
构建末尾会打印 `Memory region … flash/sram/psram` 三段占用，**SRAM 一旦 100% 会直接链接失败**（不是运行时问题）。

> ⚠️ **不要全局打开 `CONFIG_DEBUG_ASSERTIONS`**：本板会在 `HAL_Init()` 之前触发断言并卡在启动阶段。
> 需要看断言/崩溃输出时，只临时打开 `CONFIG_SYSLOG_CONSOLE=y`。

## 3. 烧录（真机）

```bash
cd ~/openvela
./flash_with_ftab.sh cmake_out/sf32lb52_lchspi_ulp_nsh_ai/nuttx.bin /dev/ttyUSB0
#   等价于：sftool 先写 ftab -> 0x12000000，再写固件 -> 0x12010000，最后读回校验
#   换 ftab：FTAB=/path/to/ftab.bin ./flash_with_ftab.sh <bin> /dev/ttyUSB0
```

要点（都是踩过的坑）：

- **顺序不能反**：ROM 先读 flash 起始 `0x12000000` 的 ftab（FlashTable），才知道二级引导在哪。
  出厂该区域是空的 —— 只烧固件不写 ftab 会一直只打印 `SFBL`。
- 启动判据：`SFBL` → **`ABCD`** → `ADC calibration…` → `NuttShell (NSH)` / `nsh>`。
  只看到 `SFBL` 没有 `ABCD` ⇒ ftab 没写进去（**不是硬件坏**，sftool 通常仍能秒连）。
- **禁止 `erase_flash`**（擦不擦都不会凭空产生 ftab，只会让排查更乱）。
- 读回校验报 **"固件 ❌ 不一致" 多数是 sftool 的已知抖动**：重试几次，或分块读回复核：

```bash
# 分块读回逐字节比对（失败重试 5 次；注意最后一块长度要按文件剩余长度算）
sftool -c SF32LB52 -p /dev/ttyUSB0 -b 1000000 --before default_reset --after no_reset \
       read_flash /tmp/rb.bin@0x12010000:16384
dd if=cmake_out/sf32lb52_lchspi_ulp_nsh_ai/nuttx.bin of=/tmp/src.bin bs=1 count=16384
cmp /tmp/rb.bin /tmp/src.bin && echo OK
```

- **`restore_code.py` 之后必须先 `touch` 再编译（2026-09-15 踩坑）**：恢复快照会**保留快照里的
  mtime**；若它比构建目录里的 `.o` 旧，ninja 认为"无需重编"而**跳过**，于是烧出混合固件
  （本次现象：倾角页有新的指针盘、原始传感器页却还是旧版式）。判据与修法：

  ```bash
  # 判据：目标文件里应当出现新符号；为 0 就是没重编
  nm cmake_out/sf32lb52_lchspi_ulp_nsh_ai/apps/examples/phywear/CMakeFiles/apps_phywear.dir/phywear_raw.c.o \
     | grep -c pw_scope_set_lanes_i16
  # 修法
  touch apps/examples/phywear/*.c apps/examples/phywear/*.h && <重新构建>
  ```
- 若板子长时间卡在启动：**先复位**；仍不行再重新烧 ftab + 固件。
- **读窗口取 16 KB**：2026-09-15 实测 64 KB / 256 KB 的单次 `read_flash` 会在 ~90% 处
  `timeout while waiting for reading flash`（读得越远越慢），而 16 KB 稳定；
  2 MB 全片逐个 16 KB 太慢，建议**按 16 KB 采样若干偏移**（首块 + 256 K/512 K/1 M/1.5 M + 末块）。
- 参考口径（2026-09-15 最后一次烧录已验证）：真机固件 `md5 c6bf6e688b34c8da162788acf61d8a92`，
  `2,064,640 B`（UI 第二批 (a)(b)(c) + 三轴页双视图修订）。
  重新编译后 md5 必然变化，请以自己构建的产物为准；上一版 `484b64ca2e9cd157a191f8ea7d022f9a`
  （2,057,968 B）留档于 `~/桌面/PhyWear-rollback-20260915-0002/firmware/nuttx.bin`。
- **无头验证交互（2026-09-15 新增）**：
  - `phywear cap rawcurve` —— 原始传感器三轴页**直接开图线视图**（配合 `pwshot.py shot rawcurve` 出真机截图，
    注意 CH340N 偶发丢字节会让 `shot` 报 `MISSING`，用 `--retries 3` 重试即可）。
  - `phywear tap <x> <y>` —— **模拟器专用**触摸注入：往 `/dev/utouch` 写
    `touch_sample_s`，先 `TOUCH_DOWN`、隔 150 ms 再 `TOUCH_UP`（一次同时带 DOWN|UP 的样本不可靠），
    这样 LVGL 的 indev 轮询能分别看到按下与抬起，产生真正的 `CLICKED`。
    真机不开 `CONFIG_UINPUT_TOUCH`，所以真机点击仍只能靠手指验证。
- **`phywear cap <页名>` 在真机上没有串口输出**（`cap` 模式不打印、心跳走 syslog 但被 GUI 抢占前
  的启动信息之外看不到）；要读真机心跳请用 `phywear cap <页名> &`，**NSH 必须用 `\r\n` 结尾**
  （只发 `\r` 或 `\n` 会回显但不执行），30 s 后出现 `[phywear] alive t=30s loops/s=NN`。

## 4. 串口与安全铁律

- 串口参数：`/dev/ttyUSB0`，**1 000 000 8N1**；CH340N 的 **RTS 直连 SoC 复位（低有效）**。
- **铁律 1**：`pyserial` 打开串口后必须立刻释放调制解调器控制线，否则板子被按在复位上：

```python
import serial
p = serial.Serial('/dev/ttyUSB0', 1000000, timeout=0.2)
p.dtr = False
p.rts = False          # 立刻释放；想主动复位再 p.rts=True -> sleep(0.2) -> False
```

- **铁律 2**：`picocom` 必须带这两个参数，否则同样会把板子按住：

```bash
picocom -b 1000000 --noreset --lower-rts --lower-dtr /dev/ttyUSB0     # 退出：Ctrl-A 然后 Ctrl-X
```

- **铁律 3**：`/dev/ttyUSB0` 独占 —— `picocom` 与脚本不能同时打开（会报
  `device reports readiness to read but returned no data`）。
- **铁律 4**：打开串口/复位都会让板子重启（RTS 接复位），属正常现象，不要当故障。
- 本机现成工具（推荐，省得自己写 pyserial）：

```bash
python3 ~/openvela/tools/phywear/boardsh.py --run "phywear micread 10" --wait 4
python3 ~/openvela/tools/phywear/boardsh.py --reset --run "ls /data"      # 需要冷启动时
```

## 6. 常见坑（按踩坑频率排序）

| # | 现象 | 原因 / 处理 |
|---|---|---|
| 1 | 同一次开机里跑第二个 `phywear`（GUI）会挂在 LCD 驱动 | 一个 boot 只跑一个 GUI 实例：**先复位再跑**。文本子命令（`tone`/`micread`）不受影响 |
| 2 | 进 GUI 后 Ctrl-C 杀不掉 `phywear` | 固件未开 `CONFIG_TTY_SIGINT`：**只能复位**（重开串口即复位） |
| 3 | 串口读报 `multiple access on port` | `/dev/ttyUSB0` 被 `picocom` 或另一个脚本占用，先释放 |
| 4 | Agent 启动后报 `No API key` / `Network timeout` | 真机无网络栈（无 WiFi/以太网驱动），属预期；端侧关键词直通与 4 个工具仍可用。`/data/agent` 目录由 Agent/PhyWear 自行创建 |
| 5 | 构建报 `aidl: not found` / `mcopy: not found` / `undefined reference to get_disp_buf` | PATH 没带上 §1 的三个目录；`get_disp_buf` 是**只有真机 LCD 驱动才有**的符号，模拟器下 `pw_shot.c` 已退化为桩 |
| 6 | 中文界面出现缺字方框 | CJK 字体子集没覆盖新文案：跑 `bash ~/openvela/tools/phywear/gen_fonts.sh` 重生成 5 个字号后重编 |
| 7 | 模拟器启动失败并报 “Running multiple emulators with the same AVD” | 上次的 qemu 还活着：`pkill -f "[q]emu-system-aarch64"`（注意用方括号写法，避免匹配到自己的命令行） |
| 8 | 真机启动只打印 `AB` / `ABCD` 后无输出 | 已修（`BSP_Board_PreInit` 时钟/晶振建立时序：XTAL32、DLL1、DLL2 各加 2 ms 等待）。若再现，先按 §3 重烧，再看 `[phywear] alive` 心跳判断 GUI 是否存活 |
